# Design: configuring backups, and custody of the repo password

Status: open
Labels: wayfinder:grilling
Blocked by: 02 (resolved), 03 (resolved)

## Question

How does a self-hoster turn on 3-2-1 backups, and how do they end up holding the
one secret that makes recovery possible?

Locked already: one repo per install; settings on the proxy container's label
via the label codec; offsite is any restic repo URL plus env vars; the password
is generated by Once, printed once, cached in the label for unattended runs, and
unrecoverable if lost. This ticket specifies:

- **Settings shape.** The struct that lives on the proxy label: local repo path,
  remote repo URL, backend credential env vars, password, enabled flag,
  last-run/last-copy/last-check timestamps. Which of these are settings versus
  observed state, and does observed state belong on the label at all?
- **Backend credentials.** The user must supply things like
  `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` or `B2_ACCOUNT_ID`/`B2_ACCOUNT_KEY`.
  How are they collected, where are they stored, and how do they reach the
  restic container - given ADR-0013 says secrets travel by environment, never
  argv. Note this is a second at-rest secret with the same exposure as the
  Tailscale credential; the ADR must say so plainly. Ticket 02 confirmed the
  exact variable names (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` for S3 and
  every S3-compatible provider, `B2_ACCOUNT_ID`/`B2_ACCOUNT_KEY` for B2) and that
  `RESTIC_PASSWORD` never touches argv - but the S3 and B2 paths were **not**
  verified end to end for lack of credentials, so the spec should treat the first
  real cloud round-trip as an implementation-time check.
- **CLI surface.** Command names and flags. Does this extend `once backup`, or
  is it a new noun (`once backups configure`, `once repo …`)? Check the existing
  command vocabulary before inventing one.
- **TUI surface.** The settings menu already has a backups form
  (internal/ui/settings_form_backups.go, settings_menu.go). Does repo config
  belong there - which is per-app - given the repo is per-install? Where do
  install-wide settings live in the TUI today?
- **Password display-once flow.** What exactly the user sees, how it is worded,
  and what stops them skipping past it. This is the moment that decides whether
  bare-metal recovery is possible at all, so it deserves prototyping rather than
  a one-line prompt.
- **Per-app opt-in.** Is every app in the install backed up, or is it per-app?
  `BackupSettings.AutoBackup` is per-app today. Reconcile that with a per-install
  repo.
- **Fate of the existing settings.** `BackupSettings{Path, AutoBackup}` and
  `TrimBackups` retire. What happens to an install that already has them set,
  and to the tar.gz files already on disk?
