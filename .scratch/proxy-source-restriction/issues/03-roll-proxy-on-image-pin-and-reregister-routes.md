# 03 - Roll the Proxy on image-pin change and re-register non-public routes

**Problem:** `Proxy.ensureRunning` starts whatever `once-proxy` container
exists and never compares its image with the pinned `proxyImage`. Bumping the
pin (ticket 04 will) leaves every existing install on the old image, and its
routes as they were registered. ADR-0016 requires existing installs to come
under the source rule, not just new deploys.

**Blocked by:** Nothing - buildable and testable now, independent of the
kamal-proxy feature. Ticket 04 needs it.

**Status:** ready-for-agent

## Agent Brief

**Category:** enhancement
**Summary:** When Once finds the Proxy running an image other than the pinned
one, roll it (keep the state volume) and re-register every non-public route
so they carry whatever route options the current Once emits.

**Current behavior:**
`Proxy.Boot` inspects the existing container and, if found, only ensures it
is running and reads its settings label. Image drift is invisible. Routes are
registered only when an app deploys/rolls.

**Desired behavior:**
- On `Proxy.Boot`, if the existing container's image is not the pinned image,
  the Proxy is removed and booted again with the same settings, exactly as
  `UpdateSettings` does today (named volume kept, so routes/certs/state file
  survive). Same port-conflict handling as a fresh boot.
- After such a roll, every Application whose route lives on the Proxy and is
  not Public (Local; Tailnet under the `nodes` topology when Tailscale is
  enabled) has its route re-registered through the same path a deploy uses,
  targeting its currently running container. Public routes and the Recovery
  Handoff route are left alone.
- Re-registration happens once, immediately after the roll, in the same
  entry point that boots the Proxy for a namespace (not on every command).
- A failed re-registration for one app is reported and does not stop the
  others.
- No roll, no re-registration when the image already matches.

**Key interfaces:**
- `Proxy.Boot` / `Proxy.ensureRunning`: image comparison against `proxyImage`
  and the remove-and-Boot roll.
- `Namespace`: whichever method sets up the namespace and boots the Proxy
  gains the "re-register non-public routes after a roll" step; it needs the
  running container per Application and the exposure/topology facts
  `registerRouting` already uses. Consider extracting the route-registration
  step of `registerRouting` so deploy and re-registration share one path.
- Integration test: boot a Proxy under a stand-in old tag (e.g. create the
  container from the same image but assert on a mismatched pin via a test
  seam), deploy a Local app, roll, assert the app still answers and its
  route was re-issued (kamal-proxy state file or `kamal-proxy list`).

**Acceptance criteria:**
- [ ] Proxy running the pinned image: no roll, no route churn (assert the
      container ID is unchanged across a second Boot).
- [ ] Proxy running a different image: container replaced, settings label
      preserved, state volume preserved, Local app still answers afterwards.
- [ ] Non-public routes are re-registered after the roll; Public and Recovery
      Handoff routes are untouched.
- [ ] `make lint`, `make test`, `make integration` green (run under
      `flock /tmp/once-integration.lock`).

**Out of scope:**
- Passing `--allow-from` (ticket 04).
- Bumping the pinned tag (ticket 04).
- Rolling app containers.
