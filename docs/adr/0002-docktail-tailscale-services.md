# Tailscale Integration via Docktail and Tailscale Services

Supersedes [ADR-0001](0001-tailscale-integration.md).

Under ADR-0001, every exposed application became its own ephemeral virtual Tailscale device through TSDProxy. That model cost a tagged-device slot per app on the user's Tailscale plan, churned the admin console with ephemeral devices, risked Magic DNS name collisions on re-registration, and required a loopback-published port just to ask TSDProxy which URLs exist. Tailscale now ships a first-party primitive for this exact use case - Tailscale Services (GA January 2026, all plans) - so we replaced the community per-container-device emulation with it. This is a clean break: upgrading Once does not migrate TSDProxy state; users re-run `once tailscale enable`.

We deploy a single **Docktail** container (`once-docktail`, image pinned exactly like the proxy) that watches the Docker daemon via a read-only socket mount and advertises containers labelled `docktail.service.*` as native **Tailscale Services** through one real `tailscaled`. The tailnet sees one device advertising `svc:` services - one per exposed application plus the Once Admin Web App - each with a stable Magic DNS name. Apps carry `docktail.service.enable/name/port` labels (port 80, HTTPS service protocol, direct container-IP proxying on the namespace network), injected and stripped by the same retrofit Roll that handled TSDProxy labels; the per-app tailnet opt-out is unchanged.

The `tailscaled` that Docktail drives comes from one of two places, decided at enable time and recorded in the settings' `mode` field. When the host already runs `tailscaled` (its socket directory is present), Once mounts that directory into Docktail and manages no daemon of its own. Otherwise Once boots an unprivileged **`once-tailscale` sidecar** from the pinned `tailscale/tailscale` image (v1.86+, required for Services) in userspace networking mode: no TUN device, no NET_ADMIN, no host networking - preserving ADR-0001's no-elevated-privileges goal even in the sidecar shape. The sidecar keeps its node state in the `once-tailscale-state` volume (retained across disable/enable so the node identity survives) and shares its socket with Docktail via a volume. Its tagged auth key is minted at enable time via the OAuth credentials, with exactly the shape the enable-time credential probe proved could be minted.

Because the sidecar (or host daemon) is a persistent node, URL discovery no longer needs TSDProxy's lookup API or its loopback port. Service FQDNs are deterministic: at enable time Once reads the tailnet's Magic DNS suffix from the local daemon (`tailscale status --json`, via `docker exec` in sidecar mode or the host CLI in host mode - the single local-daemon seam) and persists it in the settings label; app URLs are computed as `https://{app}.{suffix}` with no live lookup. Everything Once reads from the daemon (suffix, serve status, funnel state) goes through that one interface, which has a canned-JSON fake for unit tests.

The OAuth client credentials (validated by an enable-time probe byte-compatible with Docktail's real API usage) are passed to Docktail, which uses them to sync Service definitions to the control plane; the loopback API port and stored API key of the TSDProxy design are gone. Funnel keeps its user-facing semantics (bounded duration, background-daemon teardown, verified activation) with `docktail.funnel.*` labels as the mechanism and the local daemon as the activation source. The hidden headscale control seam remains, repointed at the sidecar: a pre-minted auth key and control URL configure the sidecar's `tailscaled`, and Docktail runs without cloud credentials, which is what lets the integration suite exercise the enable/disable lifecycle against headscale with no real tailnet.
