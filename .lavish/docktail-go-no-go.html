Key relief from research: the sidecar needs zero extra privileges (userspace mode, plain bridge network) — Once's "no host deps, no privileged containers" principle survives in both topologies. And URL discovery gets simpler: FQDNs are deterministic (https://{app}.{tailnet-suffix}), computed from one value read off the local daemon at enable time.

The evidence — five research tickets

Free Personal plan

pass — hard bar cleared

Tailscale Services is GA since Jan 2026 on all plans including free Personal. No service-count cap published or enforced. Residual risk: plan-based limits are announced as future work, with a "legacy exception" promised for existing usage.

issues/01-research-services-free-plan.md

Unprivileged sidecar

pass

A tailscale/tailscale container in userspace mode (no TUN, no NET_ADMIN, no host networking) on the shared app bridge network can advertise Services and serve Funnel. Docktail's documented sidecar compose is over-privileged and can be trimmed. Needs tailscale v1.86+.

issues/02-research-userspace-sidecar.md

Headscale test seam

lost

Headscale supports neither Services nor serve/Funnel; the gap is tracked (issue #2845, milestone v0.34.0) but current release is v0.29.2 with no PRs — years away at best. Testing means faking the tailscale CLI/socket and stubbing the cloud API, byte-compatible with docktail's real calls.

Follow-up (ticket 09): Services is separable from the cert machinery in principle (only the HTTPS flavor needs certs), but headscale has zero Services surface and its strict policy parser rejects svc: / autoApprovers.services outright — fake-seams is locked in. Silver lining: headscale does expose GET/PUT /api/v1/policy (bearer key, DB mode) accepting the same HuJSON for the shared sections, so ACL automation stays testable on the seam minus Services vocabulary.

issues/03-research-headscale-services.md · issues/09-research-headscale-partial-support.md

URL discovery

simpler than today

Service FQDNs are deterministic. Read .CurrentTailnet.MagicDNSSuffix from the local tailscaled once at enable, persist it, compute https://{app}.{suffix}. Replaces the tsdproxy REST API and the old issue-15 probe. Advertised-vs-approved status: tailscale serve status --json locally, cloud GET .../services/{svc}/devices as the authoritative approval check.

issues/04-research-url-discovery.md

Tailnet-side prerequisites

the real cost

Setup burden roughly triples vs tsdproxy — see the risk section below. Once can probe OAuth scopes and tags, detect pending approvals and funnel-attr failures; it cannot edit the user's ACL policy.

Resolved by ticket 08 — Once can fix it via API. The earlier claim that ACL edits were manual-only was wrong. GET/POST /api/v2/tailnet/{t}/acl round-trips HuJSON with comments preserved; ETag If-Match prevents clobbering concurrent edits; and Tailscale's own hujson AST library patches just the four sections, leaving hand-edited policy byte-identical.

How once tailscale enable would apply the policy (ticket 08's sketch)

  1. Offer: "Once needs 4 policy sections. Apply them via the Tailscale API? [y/N]" — No prints the copy-paste snippet.
  2. Yes prompts for a separate one-shot policy_file-scoped OAuth credential — never added to the stored runtime client (that scope can rewrite the entire tailnet policy).
  3. GET /acl, patch only tagOwners / autoApprovers.services / grants / nodeAttrs via hujson, idempotently.
  4. Show a unified diff + a GitOps warning (GitOps-managed tailnets silently overwrite API writes and this is undetectable — those users should commit the snippet instead), then confirm.
  5. POST /acl/validate dry-run, then POST /acl with If-Match; 412 → refetch and retry; any failure degrades to printing the snippet.

Your follow-ups: burden, OAuth provisioning, security

1. What's the user's burden now?

One-time, at enable: create OAuth credentials in the admin console, paste them into Once, and answer one y/N on the ACL diff. No hand-editing of policy sections, no ongoing burden. Before api-write the flow was "create credentials and correctly hand-edit 4 ACL sections"; now the ACL half is a confirmation prompt.

2. Can the API create the OAuth clients too?

Yes — since May 2025 (tailscale/tailscale#9632 closed: POST /api/v2/tailnet/{t}/keys creates OAuth clients; Terraform has a tailscale_oauth_client resource). The creating credential needs the oauth_keys scope. So Once could ask for one bootstrap credential and mint the runtime client + one-shot policy client itself — shrinking the console step to a single client creation. Zero console steps is impossible: the first credential always has to come from somewhere (chicken-and-egg).

3. Security implications

  • policy_file scope can rewrite the entire tailnet policy — a leak means lockout or tailnet-wide access grants. Mitigations already in the sketch: one-shot use, never stored, 1-hour token expiry, diff + confirm, If-Match.
  • oauth_keys scope is effectively admin-equivalent: it can mint further credentials. If Once auto-provisions clients, that bootstrap credential is the crown jewels — same treatment: use once during enable, never persist, suggest revoking it after.
  • Only the minimal-scope runtime client (auth keys + services + device read) is ever stored on the server. Setup-time powers never live on disk.
  • Open detail for the spec: whether an API-created client's scopes must be a subset of its creator's (attenuation) — determines if one bootstrap credential can safely mint both clients.

Weighing it

For docktail

  • One tailnet device instead of one per app — no device-slot consumption, clean admin console
  • Native Services is the first-party primitive; tsdproxy's virtual-device emulation is a community workaround
  • No per-app node state volume, no ephemeral-node lifecycle quirks, no name-collision workarounds
  • URL discovery becomes pure computation — deletes the REST-API lookup and the loopback port exception
  • Sidecar stays fully unprivileged; the ADR's security posture holds

Against docktail

  • Tailnet setup burden ~3×: 3 OAuth scopes, up to 4 ACL sections, manual admin-console edits
  • Default allow-all policy silently excludes Services — guaranteed onboarding friction
  • Headscale integration-test seam dies; real control-plane coverage drops to fakes
  • Requires a real tailscaled (host install or sidecar) — one more container in the sidecar case
  • Rewrite of ~2,200 lines of integration surface + clean break for existing installs
